# vue_musicplayer：2026.9—2027.1 项目升级路线图

> 制定日期：2026-08-23  
> 适用周期：2026-09-01—2027-01-31  
> 建议投入：每周 8—10 小时，约 180—220 小时  
> 项目定位：以 Java 全栈工程能力为主线，以可评测的 AI 音乐助手为差异化亮点  
> 本文是这一时间段的唯一执行计划；`修改建议.txt` 和 `全盘审计报告.md` 只作为历史问题地图。

## 1. 先说结论

这个项目已经不是“从零做一个音乐播放器”，而是一个有较完整业务骨架的模块化单体。未来五个月最有价值的方向不是继续换框架、盲目拆微服务，而是补齐一条可证明的工程闭环：

**需求与设计 → 开发 → 自动化测试 → CI/CD → Linux/HTTPS 部署 → 监控与压测 → AI Agent/RAG → 评测与作品集。**

推荐形成两条能力线：

1. **主线（必须做深）**：Vue 3 + TypeScript + Spring Boot + MySQL + Redis + Testcontainers + Vitest/Playwright + Docker + GitHub Actions + OpenTelemetry。
2. **差异化线（主线稳定后再做）**：Python FastAPI + LangChain/LangGraph + Qdrant + Tool Calling + RAG + Agent Evaluation。

AI 服务是唯一建议引入的独立服务：它与 Java 业务服务语言、依赖、扩缩容方式都不同，边界真实；用户、歌曲、歌单、队列仍留在 Spring Boot 模块化单体中，不为“微服务”而拆微服务。

## 2. 当前项目现状（以代码和本次验证为准）

### 2.1 已有资产

- 前端：Vue 3、TypeScript、Vite、Pinia、Vue Router、Element Plus、Tailwind CSS、VueUse、Axios；共约 34 个 Vue 文件、65 个 TypeScript 文件。
- 后端：Java 21、Spring Boot 3.5、Spring Security、MyBatis-Plus、Flyway、JWT、Redis、MySQL；约 125 个主代码文件。
- 业务：用户注册/登录/资料、歌曲上传/搜索/编辑、歌词、歌单、收藏歌单、播放队列、播放状态与多种播放模式。
- 安全与数据：BCrypt、JWT 黑名单、登录限流、上传文件校验、统一异常处理、V1—V8 数据迁移、关键外键和唯一约束。
- 基础设施：多阶段 Dockerfile、Docker Compose、Nginx 静态资源与反向代理、MySQL/Redis 健康检查。
- 测试：11 个后端测试类，包含单元测试、Spring 上下文测试和 Testcontainers MySQL 迁移测试。
- 播放器特色：Media Session、Web Audio 可视化、歌词滚动、队列拖拽、进度与播放状态同步。

这些内容足以作为继续深化的基线，不需要改成 React、重写 ORM、重建数据库或更换主键生成方式。

### 2.2 当前真实缺口

| 领域 | 当前状态 | 影响 |
|---|---|---|
| 可复现构建 | 前端 type-check、lint 通过；生产构建本次在生成 `components.d.ts` 时遇到 Windows 文件写入错误 | 不能宣称构建稳定 |
| 后端测试 | 26 个测试中 25 个通过；Flyway Testcontainers 用例因本机 Docker 不可用失败 | 测试依赖条件未被脚本和文档处理好 |
| 配置 | `compose.yml` 要求 `MYSQL_APP_PASSWORD`、`JWT_SECRET`，根 `.env.example` 却使用另一组变量且缺 JWT | 新环境无法照 README 一次启动 |
| 前端测试 | 没有 Vitest、Vue Test Utils、MSW、Playwright/Cypress | 页面重构和播放器状态缺少回归保护 |
| CI/CD | 没有 `.github/workflows` | 本地通过不等于仓库质量门禁通过 |
| API 契约 | 没有 OpenAPI/Swagger，也没有自动生成客户端 | 前后端字段错位靠运行时发现 |
| 可观测性 | 没有 Actuator、Micrometer、Prometheus、OpenTelemetry | 出问题只能翻普通日志 |
| 业务骨架 | tags、comments、play_history 等已有表/类，但部分 Service 只有空壳且没有用户闭环 | 数据模型存在，产品能力不存在 |
| 推荐/AI | 没有推荐、LLM、Agent、RAG、向量库或评测 | 缺少差异化亮点 |
| 部署证据 | 有 Compose，但没有线上 HTTPS、备份恢复、回滚、压测报告 | “会部署”缺少可验证证据 |

### 2.3 需要先复核的技术债

旧审计报告基于更早的提交，很多项已经修复，不能整份照抄执行。9 月只复核仍可能影响主链路的内容：

- 队列增删、重排、从歌单创建队列的数据库一致性与事务边界。
- 私有歌单、歌曲编辑、队列操作的对象级权限，避免 IDOR。
- 401 后前端内存状态、本地存储和路由状态能否同时清理。
- 客户端 SHA-256 再由服务端 BCrypt 的历史兼容逻辑：最终应依赖 HTTPS 传输，服务端使用 BCrypt/Argon2，删除可重放的客户端哈希方案。
- 本地文件和数据库写入失败时的补偿；播放历史的幂等与“有效播放”定义。
- `fullstack-starter/` 与主项目的职责：若不是要维护的模板，归档或移出主仓库，避免 CI、Sonar、依赖扫描混入两套应用。

## 3. 2027 年 1 月底的目标架构

```text
Browser / Vue 3
       |
       | HTTPS + JWT / SSE
       v
Nginx ----------------------> static audio / covers
       |
       v
Spring Boot 模块化单体（系统事实源、鉴权、业务 API、AI BFF）
       |             |                    |
       v             v                    v
    MySQL          Redis          Python AI Service（内网）
                                        |
                              FastAPI + LangChain/LangGraph
                                        |
                              LLM API / Ollama + Qdrant

GitHub Actions -> test -> image -> scan -> deploy
Spring/Python -> OpenTelemetry Collector -> metrics/logs/traces backend
```

关键边界：

- AI 服务不直接读写 MySQL，只通过受鉴权、可审计的 Java 内部 API 调用业务能力。
- Java 服务继续负责用户身份、权限、数据一致性和写操作确认。
- Vue 只访问 Nginx/Spring Boot；AI 服务不直接暴露到公网。
- 所有 Agent 写操作先生成预览，用户确认后再执行，不能让模型直接创建或删除数据。
- LLM 提供商通过兼容接口配置，避免把业务代码绑死在单一模型上。

## 4. 技术栈优先级与性价比

### P0：必须掌握并产出证据

| 技术/能力 | 为什么值得做 | 最终证据 |
|---|---|---|
| Spring Boot、事务、MyBatis、SQL/索引 | Java 后端岗位最核心，项目已有基础，继续做深成本最低 | 业务集成测试、慢 SQL 与优化报告 |
| TypeScript、Vue 组件与状态测试 | 补足当前最大质量短板 | Vitest/组件测试和核心 UI 回归 |
| Testcontainers | 用真实 MySQL/Redis 验证方言、迁移和事务 | CI 中稳定运行的集成测试 |
| Playwright | 用用户视角证明全链路可用 | 5—8 条稳定 E2E 冒烟链路 |
| Docker Compose、Nginx、Linux、HTTPS | 全栈项目必须真正上线 | 可访问地址、部署与回滚 runbook |
| GitHub Actions | GitHub 仓库已有远端，投入小、展示直观 | PR 质量门禁、镜像构建和发布流水线 |
| Actuator/Micrometer/OpenTelemetry | 从“能跑”升级到“能定位问题” | 指标面板、trace、告警或故障复盘 |
| k6 与性能分析 | 让 Redis、索引、线程池优化有数据依据 | 同环境优化前后对比数据 |

### P1：差异化能力

| 技术/能力 | 推荐程度 | 用法 |
|---|---|---|
| FastAPI + Pydantic | 高 | 独立 AI 服务、明确请求响应模型、异步流式接口 |
| LangChain | 高 | 模型、工具、Retriever、Prompt 等通用抽象 |
| LangGraph | 高 | Agent 状态机、持久化、重试、Human-in-the-loop；不要只写无限 ReAct 循环 |
| Qdrant | 中高 | 保留 MySQL，不为向量检索强行迁库；保存歌词/标签/歌单描述向量与 metadata |
| RAG Evaluation | 高 | 检索命中率、忠实度、工具成功率、越权率和延迟，比“接了大模型”更有含金量 |
| SSE | 高 | 流式输出、工具执行阶段展示；比 WebSocket 更符合单向生成流 |
| MCP | 中 | 1 月有余力时把只读音乐工具暴露为 MCP Server，属于扩展项，不是 Agent MVP 前置条件 |
| S3/MinIO | 中 | 若真实部署遇到本地磁盘迁移/备份问题，再改成对象存储和预签名 URL |

### P2：2027 年 1 月前不做

- 不把 user/song/playlist/queue 拆成多个微服务。
- 不为了简历同时加入 Kafka、RabbitMQ、Elasticsearch、gRPC、Kubernetes、Service Mesh。
- 不同时维护 Spring AI 和 LangChain 两套 Agent 实现。
- 不训练或微调大模型；项目数据量和目标都不支持它成为高性价比主线。
- 不做复杂社交、支付、版权分发等会改变项目边界的功能。

如果以后出现明确需求再引入：大量异步事件才考虑 Kafka/RabbitMQ，多实例和复杂发布才考虑 Kubernetes，搜索规模与相关性不足才考虑 Elasticsearch。

## 5. 五个月执行计划

### 2026.09：基线、契约、安全与核心数据闭环

目标：任何新机器和 CI 都能验证项目；补出推荐和 Agent 所需的可靠数据。

#### W1（9.1—9.6）：让基线真正变绿

- 修正根 `.env.example`、Compose 变量名和 README，使 `Copy-Item .env.example .env` 后只需填密钥即可启动。
- 定位 `components.d.ts` 写入失败：确认是否 IDE/防病毒占用、自动生成插件并发或生成文件策略问题；保证连续两次 `pnpm build` 通过。
- 为 Docker 不可用时给出明确前置检查；Testcontainers 测试在 CI 必须执行，本地可以通过 profile 清晰区分单元测试与集成测试。
- 建立 `scripts/verify.ps1` 或等价命令入口：前端 type-check/lint/build，后端 unit/integration test，Compose config。
- 复核旧审计 P0 项，只把仍能复现的项转成 GitHub Issues；已修复项关闭并注明验证证据。

验收：全新环境按 README 能启动；验证命令连续两次通过；仓库不再有两份互相矛盾的配置说明。

#### W2（9.7—9.13）：API 契约与安全收口

- 接入 springdoc-openapi，整理统一错误码、分页结构、ID 序列化和日期格式。
- 先用 OpenAPI 校对前后端类型；若自动生成客户端改造量过大，本月只生成类型，不重写全部 API 层。
- 迁移并删除客户端 SHA-256 密码方案；HTTPS 下传输密码，服务端 BCrypt；保留一次性旧数据迁移测试。
- 补对象级权限测试：私有歌单、他人上传、他人队列、用户资料。
- 明确 JWT 存储和刷新策略。五个月内优先完成短期 access token + 安全退出；只有能完整处理 HttpOnly/SameSite/CSRF 时才加入 refresh token。

验收：OpenAPI 可访问；认证、越权、错误码有自动化测试；日志不记录 token、密码和敏感工具参数。

#### W3（9.14—9.20）：标签与歌曲收藏

- 用新 Flyway 迁移补齐需要的约束/索引，不修改 V1—V8。
- 完成标签查询、歌曲标签关联、按标签筛选；上传和编辑页支持多选标签。
- 新增歌曲收藏关系、幂等收藏/取消、我的收藏分页；不要把“收藏歌单”误当成歌曲收藏。
- 后端覆盖正常、重复、越权和并发边界；前端覆盖加载、空、失败和重试状态。

验收：标签和歌曲收藏从数据库、API、页面到测试形成闭环。

#### W4（9.21—9.30）：播放历史与推荐 v1

- 定义有效播放事件，例如播放达到 30 秒或歌曲时长 50% 后记一次；上报带 eventId，服务端幂等。
- 完成历史分页、删除、清空、隐私开关和“从历史播放”。
- 先实现可解释的规则推荐：收藏/历史标签加权 + 热门度 + 时间衰减 + 排除近期重复；冷启动返回热门与多样化内容。
- Redis 只缓存热门榜和推荐结果；写操作后精确失效，Redis 故障时回源 MySQL 并记录指标。

验收：推荐结果返回 `reason`；同一输入可解释、可测试；缓存命中、回源、失效和降级都有测试或指标。

### 2026.10：建立测试金字塔

目标：新增功能不再依赖手工点页面回归。

#### W5—W6（10.1—10.18）：后端测试深化

- 用 JUnit 5 + Mockito 测纯业务规则，用 MockMvc 测鉴权/DTO/错误响应，用 Testcontainers 测 mapper、事务、Flyway、MySQL/Redis 行为。
- 优先覆盖队列重排、从歌单建队列、收藏幂等、播放历史幂等、推荐缓存和权限，而不是给 getter/setter 凑覆盖率。
- 加 JaCoCo 报告，但门禁采用“新增代码覆盖率 + 核心模块分支覆盖率”，不追求虚假的全局 100%。
- 对并发敏感操作至少写一组重复收藏/重排冲突测试。

目标值：核心业务分支覆盖率不低于 70%；所有 Flyway 迁移在真实 MySQL 容器执行。

#### W7（10.19—10.25）：前端单元与组件测试

- 接入 Vitest、Vue Test Utils、Testing Library（可选其一作为主要查询风格）和 MSW。
- 优先覆盖 `useAsyncTask`、分页、认证、播放器状态转换、请求竞态、队列乐观更新与回滚。
- 组件测试覆盖歌曲表、播放控制、创建歌单、空/错/加载态；避免大量脆弱 snapshot。

目标值：20—30 个高价值测试；核心 composable 和状态转换有失败路径测试。

#### W8（10.26—10.31）：Playwright E2E

- 建立固定测试数据和隔离账号，测试可重复执行并自动清理。
- 覆盖：注册/登录、搜索与播放、上传与编辑、创建歌单并加歌、队列重排、收藏/历史/推荐。
- CI 失败时上传截图、trace 和视频；只在必要位置等待可观察状态，不写固定长 sleep。

目标值：5—8 条稳定主链路，连续运行 5 次无随机失败。

### 2026.11：CI/CD、真实部署与可恢复性

目标：从提交代码到线上版本形成自动、可回滚的流程。

#### W9（11.1—11.8）：GitHub Actions 质量门禁

- PR 流水线并行执行前端检查、后端单元/集成测试、镜像构建。
- 使用依赖缓存但不缓存构建结果；固定 Actions 主版本，最小化 token 权限。
- 加依赖漏洞扫描和容器扫描（如 Dependabot + Trivy），生成 SBOM；高危漏洞阻断发布，普通告警进入 issue。
- 分支保护要求检查通过后才能合并。

验收：故意制造 lint、迁移和 E2E 错误时，CI 能分别阻断并提供可定位产物。

#### W10（11.9—11.15）：Linux + HTTPS 部署

- 使用一台 Linux 云主机/虚拟机，非 root 用户、SSH key、防火墙、最小端口暴露。
- Nginx 配置 HTTPS、反向代理、安全响应头、上传大小和合理限流。
- 密钥只通过服务器环境或 CI Environment Secret 注入，不写进镜像、仓库或前端。
- 镜像用不可变 tag（提交 SHA/版本），保留上一个可用版本；发布失败自动或手动一键回滚。

验收：公网/校园网可访问 HTTPS；从 tag 到部署可追溯；回滚演练成功。

#### W11（11.16—11.22）：备份、恢复和数据生命周期

- MySQL 做定时备份并验证恢复，不以“生成了 SQL 文件”作为完成。
- `static/` 与数据库采用一致的备份时间点；记录恢复顺序、RPO、RTO。
- 演练服务器重建、数据库迁移失败回滚、旧镜像恢复。
- 只有本地文件确实妨碍多机迁移或备份时，才把文件迁到 MinIO/S3 兼容存储。

验收：在空目录/空主机恢复出可登录、可播放的数据副本；记录实际恢复耗时。

#### W12（11.23—11.30）：可观测性第一阶段

- Spring 加 Actuator/Micrometer；统一 JSON 日志、requestId/traceId，敏感数据脱敏。
- 接入 OpenTelemetry，至少贯通 HTTP、MySQL、Redis；用 Collector 导出，避免业务代码绑定观测后端。
- 建立最小面板：吞吐量、p95/p99、错误率、JVM、HikariCP、Redis、登录失败、缓存命中率。
- 定义 2—3 个告警，例如 5xx 比例、后端不可用、数据库连接池耗尽。

验收：从一次前端请求能定位到 Java、SQL/Redis span 和对应日志。

### 2026.12：性能基线与 AI Agent MVP

目标：先用数据优化，再完成一个安全、可解释、可流式展示的 Agent。

#### W13（12.1—12.6）：k6 压测与优化报告

- 分开测登录、歌曲列表/搜索、推荐、播放状态写入；音频静态 Range 请求单独测，不与 Java API 混在一起。
- 固定机器规格、数据量、并发模型和测试脚本，记录吞吐、p95/p99、错误率、CPU/内存、SQL 和缓存命中。
- 只优化证据指向的问题：索引、N+1、大字段、连接池、缓存、序列化或 Nginx。

建议目标（必须附测试环境）：常用读 API 在 100 VU 下 p95 < 200ms、错误率 < 1%；不能达到时如实写基线和瓶颈。

#### W14（12.7—12.13）：AI 服务骨架与工具契约

- 建立 `ai-service/`：FastAPI、Pydantic、pytest、httpx、统一配置、健康检查、Dockerfile。
- Spring Boot 作为 AI BFF：验证用户身份，把最小必要上下文传给 AI 服务。
- LangChain 负责模型/工具/Retriever 抽象；LangGraph 定义显式状态和节点，不让模型自由访问数据库。
- 第一批只读工具：`searchSongs`、`getLikedSongs`、`getPlayHistory`、`recommendSongs`、`getPlaylist`。
- 工具输入使用 JSON Schema/Pydantic 校验；超时、重试、最大步数和 token/cost budget 都有限制。

验收：使用 fake model 能在无真实密钥的 CI 中稳定测试工具选择与参数校验。

#### W15（12.14—12.20）：流式 Agent 与可观察执行过程

- 通过 SSE 返回阶段事件：思考摘要不可暴露，展示“正在搜索歌曲/读取历史/生成推荐”等工具状态和最终结果。
- 保存会话、runId、工具名、耗时、结果摘要、错误类别；默认不保存完整敏感参数。
- 把 Agent run 串进 OpenTelemetry trace，关联 Vue → Spring → FastAPI → 工具 API。
- 处理模型超时、限流、无结果、非法参数和服务降级；AI 不可用时普通播放器仍正常工作。

验收：一次 Agent 请求可流式展示、可追踪、可取消；断开连接不会继续无限消耗模型额度。

#### W16（12.21—12.31）：Human-in-the-loop 写操作

- 增加 `previewPlaylist`，只返回建议名称、歌曲与原因，不写数据库。
- 用户确认后，由前端携带短期 confirmationId 调用 `createPlaylist`；服务端再次校验用户、歌曲和过期时间。
- confirmationId 一次性、幂等、可审计；模型不能伪造确认或跨用户使用。
- 建立提示注入测试：歌词、歌单描述或用户输入中的指令不能改变系统权限或直接触发写操作。

验收：未确认、重复确认、过期确认、跨用户确认全部被拒绝；正常确认只创建一次。

### 2027.01：RAG、评测、打磨与简历材料

目标：不是“接入向量库”，而是证明检索和 Agent 在一组固定任务上有效。

#### W17（1.1—1.10）：一个有边界的 RAG 场景

推荐场景：**自然语言找歌与歌单问答**，检索歌曲元数据、标签、用户有权访问的歌单描述，以及允许处理的歌词片段。

- Qdrant 保存 embedding、documentId、owner/visibility、songId、chunk 类型、版本等 metadata。
- 设计 ingestion：新增/编辑/删除后异步更新向量；失败可重试并能重建索引。
- 对歌词按段落/时间片切块，对短元数据合并成单文档；不要机械固定 500 token。
- 检索先做 metadata 权限过滤，再做向量/混合检索；响应给出歌曲和命中文档来源。
- 不把未经许可的版权歌词提交进 Git 或公共数据集。

验收：删除或设为私密的数据不会被其他用户检索；索引可从 MySQL 事实数据完全重建。

#### W18（1.11—1.17）：Agent/RAG 评测体系

- 建立至少 50 条版本化评测集：精确找歌、模糊偏好、空结果、歧义、越权、提示注入、重复写入、模型超时。
- 检索指标：Recall@5、MRR 或 nDCG；生成指标：groundedness/relevance；Agent 指标：工具选择成功率、参数正确率、任务成功率、越权写入率、p95 延迟和单次成本。
- 单元测试使用 fake model；小规模 nightly/手动评测才调用真实模型，避免每个 PR 消耗额度和产生随机失败。
- 可使用模型裁判，但关键安全断言必须是确定性代码，不能只信 LLM-as-a-judge。

建议闸门：Recall@5 ≥ 0.80、只读任务成功率 ≥ 85%、未确认写入为 0、跨用户数据泄露为 0。数值不达标就修检索/工具/提示，不增加更多功能。

#### W19（1.18—1.24）：产品与体验收口

- 移动端基本适配、键盘操作、aria-label、颜色对比度、加载/空/失败/重试状态。
- 优化首屏和大组件加载，分析 bundle；播放器错误、stalled、网络恢复和资源释放可见且可测试。
- 邀请 3—5 位同学完成固定任务，记录完成率、失败点和一轮改进，不只收集“好不好看”。
- 修复高影响问题，冻结功能，不在最后一周再引入新中间件。

#### W20（1.25—1.31）：作品集发布

- 打 `v1.0.0` tag，发布架构图、ER 图、关键时序图、OpenAPI、部署 runbook、压测报告、Agent 评测报告。
- 录制 3—5 分钟演示：普通业务 → CI → 线上监控 → Agent 工具/RAG → 确认创建歌单。
- 准备两个故障故事：一次数据一致性/事务问题，一次部署/性能/Agent 安全问题；说明定位证据和权衡。
- 简历只写已经完成并能演示的数据，指标注明测试环境。

## 6. 每项功能的完成定义（Definition of Done）

一项功能只有同时满足以下条件才算完成：

- 有明确用户场景、边界和非目标；重要取舍写一页 ADR。
- 数据变更只新增 Flyway 迁移，并有真实 MySQL 迁移测试。
- API 有 DTO 校验、OpenAPI、统一错误码、鉴权和对象级权限。
- 后端有业务/接口/集成测试；前端有关键状态测试；主链路有 E2E。
- 页面包含正常、加载、空、失败、重试和无权限状态。
- 日志不泄露敏感信息；关键路径有 metric/trace；失败可诊断。
- Compose 和线上环境均验证；配置、升级和回滚文档同步更新。
- PR 小而可审查，提交信息说明“为什么”，不是只写“修改代码”。

## 7. 阶段闸门与降级方案

### 必须遵守的闸门

- 9 月基线未稳定，不开始大规模业务功能。
- 10 月核心业务没有自动测试，不开始 AI 服务。
- 11 月没有 CI、HTTPS、备份恢复，不接入真实生产模型密钥。

- 权限过滤和评测集未通过，不公开 RAG 功能。

### 进度落后时怎么砍需求

按以下顺序删除，不能牺牲测试和部署来保留炫技功能：

1. 先砍 MCP、MinIO/S3、评论、i18n、WebSocket“一起听”。
2. 再砍复杂混合检索，只保留 Qdrant 向量检索 + metadata filter。
3. 再把 LangGraph 缩成固定的“检索/工具 → 预览 → 确认”三段图。
4. 若 12 月主线仍不稳定，取消 Python 独立服务，改用 Spring AI 在 Java 内完成只读 Tool Calling；不要同时留下两套半成品。

第一部分：现有功能 Bug 修复 & 体验优化（来自原有建议 + 新发现）
═══════════════════════════════════════════════════════════════════════════════

1. 登录过期提示
   - 问题：JWT token 过期后无用户提示，静默跳转到登录页
   - 方案：axios 拦截器在 401 时弹出 ElMessage.warning("登录已过期，请重新登录")，再跳转

2. 鼠标悬停时文字全白看不清
   - 问题：某些组件悬停态颜色对比度不足（如歌曲列表行 hover 时文字变白与浅色背景冲突）
   - 方案：检查各组件 hover 样式，确保文字色与背景色有足够对比度

3. 翻页时重置窗口位置
   - 问题：歌曲列表/歌单列表切换页码后，页面不自动滚动到顶部
   - 方案：在分页组件的 @current-change 事件中调用 window.scrollTo(0, 0)

4. 内存管理优化
   - 问题：页面销毁时没有清理定时器、事件监听、未完成的网络请求
   - 方案：
     - 每个组件 onBeforeUnmount 中清理 setInterval/setTimeout
     - playerStore 的 fadeTimer 在组件卸载时清理
     - axios 请求使用 AbortController（已有基础但可加强）
     - 大对象（如歌词数组、队列列表）在离开页面时置 null

5. 响应式布局及多端适配 + Token 机制优化
   - 问题：目前主要适配桌面端，移动端体验差；Token 存储在 localStorage 有 XSS 风险
   - 方案：
     - 使用 Tailwind 响应式类（sm/md/lg/xl）适配移动端
     - 底部播放栏在移动端改为固定底部迷你条
     - QueueDrawer 在移动端改为全屏
     - Token 考虑 httpOnly cookie + refresh token 双 token 机制（后端配合）
     - 短期方案：Token 保持 localStorage 但加入过期检测和自动刷新

6. localStorage 操作迁移到 Store 中
   - 问题：userApi 和组件中直接操作 localStorage，逻辑分散
   - 方案：所有 localStorage 读写统一收敛到 userStore 中，组件只通过 store 访问

7. 导航栏显示用户头像
   - 问题：NavBar 目前只显示用户名，没有头像
   - 方案：NavBar 用户下拉按钮处显示 user_cover_url 头像（用 el-avatar），默认显示首字母

8. 歌曲编辑页面未显示当前封面
   - 问题：EditUserUploadSongs.vue 编辑时没有预览已有封面图
   - 方案：进入编辑页时加载并显示当前歌曲的 song_cover_url 缩略图

9. 刷新功能
   - 问题：无页面数据刷新按钮
   - 方案：各列表页（歌曲、歌单、上传歌曲）顶部增加刷新图标按钮，重新请求数据

10. [新发现] /api/stats 统计接口后端未实现
    - 文件：web/src/api/choreApi.ts 调用了 getStatics()，但后端无对应 Controller
    - 方案：后端实现 StatsController，返回 total_songs, total_users, online_users 等统计数据；或暂时移除前端调用

11. [新发现] Redis 已配置但完全未使用
    - 文件：backend/.../config/RedisConfig.java 配置了 Redis 连接
    - 方案：利用 Redis 缓存热门排行榜、热门歌单等高频查询数据

12. [新发现] 播放状态同步间隔过长
    - 文件：web/src/stores/player.ts 中 SYNC_INTERVAL = 500000（约 8.3 分钟）
    - 方案：建议缩短到 30000（30 秒）或 60000（1 分钟），且播放停止时立即同步

13. [新发现] 多个 Controller 空壳
    - QueueItemsController、PlayStateController、SongsPlaylistsRelationController 等为 MyBatis-Plus 自动生成但未填充
    - 方案：如无独立使用场景，可删除空壳；或补全实现

14. [新发现] 环境变量命名不一致
    - EditUserUploadSongs.vue 中使用 VITE_API_BASE_URL，其他地方用 VITE_API_URL
    - 方案：统一为一个环境变量名

15. [新发现] 客户端密码哈希方式不统一
    - userApi.ts 使用 Web Crypto API，crypto.ts 使用 CryptoJS，两者都做 SHA-256
    - 方案：统一用一种方式，推荐保留 Web Crypto API（浏览器原生，体积更小）

P0-1. 音乐标签/分类系统
  为什么需要：没有标签就无法组织内容、无法筛选、无法做推荐。这是内容网站的根基。

  数据库新增：
    -- 标签字典表
    CREATE TABLE tags (
        tag_id    INT AUTO_INCREMENT PRIMARY KEY,
        tag_name  VARCHAR(50) NOT NULL UNIQUE,
        tag_type  ENUM('genre','language','mood','scene','era') NOT NULL COMMENT '流派/语种/心情/场景/年代',
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );

    -- 歌曲-标签关联表 (多对多)
    CREATE TABLE song_tags (
        song_id INT NOT NULL,
        tag_id  INT NOT NULL,
        PRIMARY KEY (song_id, tag_id),
        FOREIGN KEY (song_id) REFERENCES songs(song_id) ON DELETE CASCADE,
        FOREIGN KEY (tag_id)  REFERENCES tags(tag_id)  ON DELETE CASCADE
    );

  后端改动：
    - 新建 TagsController: GET /api/tags（获取全部标签列表）、GET /api/tags?type=genre（按类型筛选）
    - 新建 SongTagsController: POST /api/songs/{id}/tags（设置歌曲标签）、GET /api/songs/{id}/tags（获取歌曲标签）
    - SongsController 上传接口支持接收 tag_ids 参数
    - GET /api/songs 接口增加 tag_id 筛选参数

  前端改动：
    - Upload.vue: 上传表单中增加标签选择器（多选，Element Plus 的 el-select multiple + el-tag）
    - Songs.vue: 搜索栏旁边增加标签筛选下拉框
    - PlaylistDetail.vue / songDetail.vue: 显示歌曲的标签徽章
    - 首页增加按标签分类浏览入口

P0-3. 播放历史
  为什么需要：用户需要找回之前听过的歌，也是推荐系统的数据基础。

  数据库新增：
    CREATE TABLE play_history (
        id         INT AUTO_INCREMENT PRIMARY KEY,
        user_id    INT NOT NULL,
        song_id    INT NOT NULL,
        played_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        INDEX idx_user_played (user_id, played_at DESC),
        FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
        FOREIGN KEY (song_id) REFERENCES songs(song_id) ON DELETE CASCADE
    );
    -- 同一用户同一首歌只保留最新一条的方式：可在插入前先 DELETE 旧记录，或用 ON DUPLICATE KEY UPDATE

  后端改动：
    - 新建 PlayHistoryController:
        GET    /api/history              -- 获取播放历史（分页，最近N条）
        DELETE /api/history/{id}         -- 删除单条历史
        DELETE /api/history              -- 清空历史
    - 播放器每次播放新歌曲时（后端 play_state 更新接口），自动写入播放历史

  前端改动：
    - router 增加 /history 路由
    - 新建 History.vue: 展示播放历史列表（按时间倒序），支持播放和删除
    - NavBar.vue 增加"播放历史"导航入口

A-1. AI 自然语言搜索
  使用场景："给我找一些适合深夜听的安静的华语慢歌"
            "有没有类似《晴天》那种风格的老歌"
            "最近上传的摇滚风格的歌推荐一下"

  技术栈：
    - LLM API（Claude/GPT）做意图识别 + 查询转译
    - LLM 将自然语言提取为结构化过滤条件（标签、语种、年代、BPM 范围等）
    - Function Calling: LLM 调用搜索 API，拿到结果后整理成自然语言回复

  后端改动：
    - 新建 AISearchController:
        POST /api/ai/search  { query: "推荐适合运动的快节奏歌曲" }
    - AISearchService:
        1. 调用 LLM 将自然语言 → 结构化筛选参数 JSON
        2. 用筛选参数查询数据库（标签匹配 + 关键词 + BPM范围等）
        3. 返回歌曲列表 + LLM 生成的推荐理由
    - 可选：将搜索结果向量化存入向量数据库，支持语义相似搜索

  前端改动：
    - NavBar 搜索框支持自然语言输入（加一个"AI 搜索"切换开关）
    - 搜索结果页显示 AI 推荐理由（如"这首歌的节奏感强，适合运动时激发动力"）
    - 支持多轮对话式搜索（上下文记忆上一轮结果）

A-2. AI 智能歌单生成
  使用场景："帮我生成一个适合雨天听的歌单，20首左右"
            "生成一个 90 年代经典粤语老歌歌单"
            "把最近一周的热门新歌整理成一个歌单"

  技术栈：
    - LLM 根据描述生成歌单名 + 描述 + 搜索条件
    - Agent 模式：LLM 自主决定调用哪些搜索/筛选 API，多轮迭代直到凑够数量

  后端改动：
    - 新建 AIPlaylistController:
        POST /api/ai/playlist/generate
          Body: { prompt: "适合下雨天听的忧伤歌曲", count: 20 }
          Response: { playlist_id, playlist_name, description, songs[], reason }
    - AIPlaylistService (Agent 流程):
        1. LLM 解析用户意图 → 拆解为多个搜索方向
           （如"雨天"→ 标签匹配"伤感/慢节奏/民谣"，同时搜索歌词含"雨"的歌曲）
        2. Agent 调用搜索 API 收集候选歌曲（Function Calling / Tool Use）
        3. Agent 对结果去重、排序、过滤
        4. LLM 为生成的歌单起名 + 写推荐语
        5. 自动创建歌单并填充歌曲
    - 高级版：加入用户偏好（播放历史、已收藏歌曲），Agent 自动避开不喜欢的风格

  前端改动：
    - Playlists.vue 增加"AI 生成歌单"按钮
    - 弹出对话框：输入自然语言描述 + 期望歌曲数量
    - 生成过程展示 Agent 的思考步骤（搜索方向、候选数量、筛选逻辑）
    - 生成完成后可预览、手动增删、确认保存
    - 增加"不满意，重新生成"和"微调"按钮（如"再慢一点"、"更多华语歌"）

A-3. AI 音乐标签自动识别
  使用场景：用户上传歌曲时，AI 自动分析音频 + 歌名/歌词，推荐标签
            （流派、心情、场景、语种），用户只需确认/微调

  技术栈：
    - 音频特征分析（可选，用 librosa/essentia）
    - LLM 分析歌名 + 歌词文本 → 推断流派/心情/场景
    - Agent 模式：LLM 多维度分析后综合判断

  后端改动：
    - 上传歌曲流程增加异步标签识别步骤：
        1. 歌曲上传完成后发送消息到消息队列（RabbitMQ）
        2. 消费者调用 LLM API，输入歌名 + 艺人 + 歌词片段
        3. LLM 返回推测的 tags: [{tag: "流行", confidence: 0.95}, {tag: "抒情", confidence: 0.8}]
        4. 自动写入 song_tags 表（只写入 confidence > 0.7 的标签）
        5. 用户可在编辑页查看/修改 AI 打的标签

  前端改动：
    - Upload.vue 上传成功后提示"AI 正在分析你的歌曲..."
    - 歌曲编辑页展示 AI 推荐标签（带置信度），用户可点击确认/删除
    - 标签旁标注 🤖 AI 推荐 vs 👤 手动设置

A-4. 与音乐库对话（RAG 知识库问答）
  使用场景："我的音乐库里一共有多少首歌？最长的一首是什么？"
            "最近一个月我听了哪些歌？哪首听得最多？"
            "帮我总结一下我歌单'睡前精选'里的音乐风格"
            "有没有哪首歌我超过一个月没听了，但以前经常听？"
            "今年我最喜欢哪首歌？"

  技术栈：
    - RAG（检索增强生成）：用户数据 → 向量嵌入 → 向量数据库（Milvus/Qdrant/Chroma）
    - LLM + Function Calling: Agent 可以查询数据库统计、播放历史等结构化数据
    - Text-to-SQL: 自然语言转 SQL 查询

  后端改动：
    - 新建 MusicChatController:
        POST /api/ai/chat  { message: "我的库里有多少周杰伦的歌？" }
        Response: { reply: "你的音乐库里有 37 首周杰伦的歌，其中...", data: {...} }
    - MusicChatAgent 核心流程:
        1. 将用户音乐数据（歌名、艺人、标签、播放历史）向量化存入向量数据库
        2. 收到用户问题 → LLM 判断需要调用哪些工具：
            - search_songs(keyword) → 搜索歌曲
            - get_statistics(type, period) → 获取统计
            - get_play_history(period) → 获取播放历史
            - get_playlist_info(id) → 获取歌单信息
            - get_user_profile() → 获取用户画像
            - run_sql(query) → 执行自定义统计查询（Text-to-SQL）
        3. Agent 多轮调用工具收集数据
        4. LLM 将结构化数据转化为自然语言回答
    - 可选的向量化：歌曲标签、歌词、歌单描述等非结构化文本做语义搜索

  前端改动：
    - 底部播放栏或 NavBar 增加"AI 助手"聊天图标
    - 点击打开侧边 AI 对话面板（类似 ChatGPT 的聊天界面）
    - 支持快捷提问按钮（"我最爱听什么？"、"推荐新歌"、"分析我的口味"）
    - 回答中嵌入可点击的歌曲卡片（播放/加入队列）
    - 侧边面板展示 Agent 的思考步骤（用了哪些工具、查了什么数据）

A-5. AI DJ（智能串烧 + 语音播报）
  使用场景：进入 AI DJ 模式后，AI 自动选曲、无缝衔接，每首歌之间插入
            AI 生成的语音介绍（类似 Spotify AI DJ / 网易云音乐私人 DJ）

  技术栈：
    - LLM 生成串词/介绍（结合歌曲背景、艺人生平、推荐理由）
    - TTS（Text-to-Speech）生成语音播报
    - Agent 根据用户当前心情/时段/历史动态决策下一首播放什么
    - Web Audio API 实现歌曲间平滑过渡（crossfade）

  后端改动：
    - 新建 AIDJController:
        POST /api/ai/dj/start    -- 启动 AI DJ 模式（返回初始曲目 + TTS 音频 URL）
        GET  /api/ai/dj/next     -- 获取下一首歌 + AI 串词音频
        POST /api/ai/dj/skip     -- 跳过当前（反馈给 Agent 调整策略）
        POST /api/ai/dj/feedback { rating: "like"|"dislike" }
          -- 用户反馈（Agent 学习偏好）
    - AIDJService (Agent 流程):
        1. Agent 获取用户画像（喜欢的标签、最近播放、当前时间、当前心情）
        2. Agent 决策下一首歌（探索 vs 利用平衡：熟悉的歌 vs 发现新歌）
        3. LLM 生成 10-20 秒的串场语音文本（结合歌曲背景 + 推荐理由）
        4. TTS 服务合成语音（OpenAI TTS / 火山引擎 / 微软 Azure TTS）
        5. 语音音频和歌曲音频拼接/排队
        6. 根据用户 skip/dislike 反馈持续调整策略
    - 实现建议：
        - DJ 串词可以做成不同的"DJ 人格"（温柔知性、幽默搞怪、专业乐评人）
        - TTS 语音缓存（同一首歌的串词复用，不用重复合成）

  前端改动：
    - 播放栏增加"AI DJ"模式按钮（类似收音机图标）
    - 进入 DJ 模式后：
        - 播放队列由 AI 动态管理（不再显示完整列表）
        - 显示"当前 AI DJ 正在为你挑选..."动画
        - 歌曲间隙显示 DJ 串词文字 + 播放 TTS 语音
        - 显示 DJ 的推荐理由卡片
        - "下一首是什么"按钮（可预览但不可完整列表）
        - 赞/踩按钮实时反馈
    - 完全替代手动选歌的懒人模式

A-9. Agent 架构设计建议
  推荐技术选型：
    - LLM: Claude API（Claude Fable 5）或 OpenAI GPT
    - Agent 框架: 后端可以用 LangChain4j（Java 生态）/ Spring AI
    - Function Calling: 定义工具集（搜索歌曲、查数据库、创建歌单等）
    - 向量数据库: Milvus（生产级）/ Chroma（轻量）/ Qdrant
    - 嵌入模型: text-embedding-3-small / 本地 BGE 模型
    - 消息队列: RabbitMQ（异步 AI 任务）
    - MCP (Model Context Protocol): 如果后续要做更复杂的 Agent 编排，
      可考虑将音乐平台的能力封装为 MCP Server，让 AI 客户端直接调用

  通用 Agent 工具集设计（所有 AI 功能共用）:
    search_songs(keyword, tags[], limit)       -- 搜索歌曲
    get_song_info(song_id)                     -- 获取歌曲详情
    get_user_stats()                           -- 获取用户统计
    get_play_history(days)                     -- 获取播放历史
    get_user_playlists()                       -- 获取用户歌单
    create_playlist(name, description, song_ids) -- 创建歌单
    get_playlist_songs(playlist_id)            -- 获取歌单歌曲
    get_hot_songs(limit)                       -- 获取热门歌曲
    get_tags(type)                             -- 获取标签列表
    analyze_lyrics(song_id)                    -- 分析歌词
    get_similar_songs(song_id)                -- 获取相似歌曲

T-11. i18n 国际化

T-12. 音频处理（FFmpeg）
  学习目标：音视频编解码、格式转换、元数据操作

  应用场景：
    - 上传歌曲自动转码为统一格式（AAC 256kbps / MP3 320kbps）
    - 提取音频片段作为预览（30 秒试听）
    - 音频响度标准化（LUFS normalization，避免不同歌曲音量差异大）
    - 音频剪辑/截取（用户自定义铃声片段）
    - 生成波形缩略图

  实现：
    - Java 调用 FFmpeg（ProcessBuilder 或 JAVE2 库）
    - 消息队列异步处理转码任务
    - Docker 基础镜像中安装 FFmpeg

───────────────────────────────────────────────────────────────────────────────
T-13. 接口限流与安全
  学习目标：限流算法、安全防护

  T-13-1. 接口限流
    - 基于 Redis + Lua 脚本的滑动窗口限流
    - 或 Spring Cloud Gateway / Sentinel 集成
    - 按用户/IP/接口维度限流
    - 上传接口严格限流（防止被刷）

  T-13-2. 安全防护
    - XSS 过滤器（评论内容过滤 script 标签）
    - CSRF 防护（如用了 Cookie 则需要）
    - SQL 注入防护（MyBatis 参数化查询已有，但需注意动态 SQL）
    - 文件上传安全（类型校验、大小限制、病毒扫描）
    - 密码强度校验
    - 登录失败次数限制（Redis 计数器）

  T-13-3. 敏感词过滤
    - DFA 算法实现敏感词库
    - 或集成第三方内容安全 API（阿里云/腾讯云）
    - 评论、歌单描述、用户名都需要过滤

───────────────────────────────────────────────────────────────────────────────
T-14. 推荐算法从零实现
  学习目标：理解推荐系统原理，不依赖现成库

  阶段一：基于内容的推荐（Content-Based）
    - 歌曲标签向量 → 余弦相似度计算 → TopN 相似歌曲
    - 用户标签偏好向量（收藏/播放历史加权） → 相似度匹配

  阶段二：协同过滤（Collaborative Filtering）
    - 基于用户的 CF：找到相似用户 → 推荐他们的收藏
    - 基于物品的 CF：歌曲共现矩阵 → A 和 B 经常被一起收藏
    - 用 Redis 存储共现矩阵，定时离线计算

  阶段三：混合推荐 + 深度学习（可选）
    - 加权融合多种推荐策略
    - 或用 DeepFM / Wide&Deep 等模型（Java 可调 Python 模型服务）

───────────────────────────────────────────────────────────────────────────────
T-15. GraphQL API
  学习目标：声明式数据查询、减少 over-fetching

  应用场景：替代部分 REST 接口，让前端灵活组合查询字段
    例如：查询歌单时可以选择是否同时返回歌曲列表、创建者信息、标签

  实现：
    - Spring Boot 集成 spring-boot-starter-graphql
    - 定义 Schema（类型、Query、Mutation）
    - 前端使用 @apollo/client 或 urql
    - 部分复杂查询用 GraphQL（如歌单详情页），简单查询保持 REST
    - REST 和 GraphQL 共存，不全部替换

───────────────────────────────────────────────────────────────────────────────
T-16. Spring Cloud 微服务化（高级阶段）
  学习目标：服务注册发现、配置中心、网关、远程调用

  注意：这是大型项目才需要的架构升级，建议在单体架构把功能做完整后再拆

  架构设计：
    - Nacos: 服务注册中心 + 配置中心
    - Gateway: API 网关（统一入口、路由转发、鉴权、限流）
    - OpenFeign: 微服务间 RPC 调用
    - Sentinel: 熔断降级
    - Seata: 分布式事务
    - SkyWalking: 分布式链路追踪

  服务拆分建议（按业务域）：
    - user-service（用户、关注）
    - song-service（歌曲、标签、歌词）
    - playlist-service（歌单）
    - queue-service（播放队列、播放状态）
    - comment-service（评论）
    - notification-service（通知）
    - recommendation-service（推荐）
    - ai-service（AI Agent 所有功能）
    - gateway-service（API 网关）
